# ТЗ: полный переход VibeCemetery на карту v2 и вывод v1 из эксплуатации

Статус: реализация начата; кодовый cutover и инструменты миграции в ветке `codex/v2-cutover`, production-переход ещё не выполнен. Ход выполнения и команды: [v2-cutover-runbook.md](v2-cutover-runbook.md).
Дата: 2026-09-07
Целевой релиз: v2 становится единственной публичной картой

## 1. Резюме решения

VibeCemetery должен полностью прекратить публичное использование карты v1 и лицензированных ассетов Kokoro Reflections. Карта v2 становится единственной публичной картой, доступной по каноническому адресу `/cemetery`.

Все существующие могилы v1 переносятся в свободные слоты v2 без изменения их UUID. Голоса F, ссылки, авторство, лимиты аккаунтов, burn intents и подтверждённые GRAVE offerings сохраняются. Новые захоронения после перехода создаются только в v2.

Интерактивная v1, публичный скриншот v1 и счётчик на 333 открытия не входят в целевую архитектуру. Оригиналы v1 сохраняются только в приватном локальном архиве вне Git и публичных хранилищ.

## 2. Причины перехода

### 2.1. Лицензия

Официальные условия Kokoro Reflections запрещают использование tileset-ассетов в blockchain- и AI-related проектах и запрещают публикацию самих ассетов в открытых репозиториях. VibeCemetery использует AI-тематику и реальные операции с токеном GRAVE, поэтому дальнейшее публичное использование v1 создаёт неприемлемый лицензионный риск.

Источники:

- https://kokororeflections.com/terms-use/
- https://kokororeflections.itch.io/kr-peaceful-rest-graveyard-tileset-for-rpgs

### 2.2. Расход Supabase

Первичная загрузка v1 передаёт около 7 МБ лицензированных файлов из Supabase Storage. Даже 333 полных загрузки дают примерно 2,33 ГБ трафика без учёта API и других запросов.

V2 загружает runtime-ассеты из `/public/map` через хостинг приложения/CDN. Текущий сырой объём TMJ и 74 изображений составляет около 2,24 MiB, при этом изображения занимают около 0,305 MiB, а TMJ хорошо сжимается HTTP-сжатием. Эти запросы не должны использовать Supabase Storage egress.

### 2.3. Упрощение продукта

Две публичные карты усложняют маршруты, ссылки, тесты, выбор слотов, поддержку мобильной версии и объяснение продукта. После перехода у проекта остаётся одна карта, одна точка входа и один тип нового захоронения.

## 3. Цели

1. Сделать v2 единственной публичной картой.
2. Сохранить все существующие могилы и связанные записи без потери идентичности и истории.
3. Исключить создание новых могил с `map_version = 'v1'`.
4. Исключить загрузку лицензированных v1-ассетов из Supabase Storage.
5. Сохранить работу GitHub-захоронений, локального агента, F, профиля, Necropolis, deep links и GRAVE offerings.
6. Обеспечить проверяемый и обратимый перенос данных.
7. Удалить v1 runtime-код и тестовую матрицу после успешного перехода.

## 4. Не входит в объём работ

- Публичная архивная страница со скриншотом оригинальной v1.
- Перепубликация или перенос ассетов Kokoro Reflections в GitHub.
- Счётчик открытий v1 или автоматическое отключение по лимиту.
- Изменение токена GRAVE, контракта, burn address или сети Base.
- Изменение общего лимита аккаунта 4 + 1.
- Создание нового NFT или токенизация изображения карты.
- Редизайн самой карты v2 и производство новых ассетов.
- Реальная тестовая отправка токенов без отдельного явного разрешения владельца проекта.

## 5. Текущее состояние

### 5.1. Приложение

- `/cemetery` рендерит `CemeteryApp` и карту v1.
- `/cemetery/v2` рендерит `CemeteryAppV2`.
- `CemeteryAppV2` устанавливает `CemeteryMapVersionContext` в `v2`.
- `BuryFlowModal` передаёт текущий `map_version` в `POST /api/graves`.
- Сервер умеет выбирать слоты v1 и v2 и назначает `grave_gid` для v2.
- `/grave/[id]` читает `map_version` могилы и отправляет пользователя на соответствующую карту.
- Главная страница и локальный burial helper пока используют v1 по умолчанию.
- Переключатель v1/v2 присутствует в `TopBar`.

### 5.2. База данных

- `graves.map_version` поддерживает `v1` и `v2`.
- Уникальность слота задана как `(slot_id, map_version)`.
- `graves.grave_gid` хранит визуальный вариант могилы v2.
- UUID могилы является основным идентификатором для `f_votes`, `grave_burn_intents` и `grave_burns`.
- Общий лимит 4 + 1 считается по аккаунту через `create_grave_once`, а не отдельно по картам.
- Согласно `docs/supabase-simplification-rollout.md`, необходимые additive-миграции уже применены к рабочей базе и проверены транзакционно. Перед релизом это необходимо подтвердить повторной read-only проверкой целевого Supabase-проекта.

### 5.3. Данные

Последняя зафиксированная инвентаризация содержит 9 могил v1. Перед выполнением миграции фактические значения должны быть получены заново; ТЗ не должно полагаться на число 9 как на неизменяемое.

## 6. Целевая архитектура

```text
Пользователь
    │
    ▼
/cemetery ──► CemeteryAppV2 ──► /map/cemetery-v2.tmj + v2 PNG (хостинг/CDN)
    │
    ├──► /api/graves ──► Supabase Database
    ├──► /api/graves/account
    ├──► /api/offerings
    └──► Base RPC для чтения/проверки добровольных GRAVE offerings

Supabase Storage tilesets: не используется
```

`map_version` остаётся в схеме для истории и будущих версий карты, но публичное приложение создаёт и показывает только `v2`.

## 7. Функциональные требования

### FR-01. Канонический маршрут

- `/cemetery` должен рендерить `CemeteryAppV2`.
- `/cemetery/v2` должен отвечать постоянным redirect на `/cemetery`.
- Если существует или появится `/cemetery/v1`, он должен отвечать redirect на `/cemetery`.
- Redirect обязан сохранять query-параметры `grave`, `modal` и будущие безопасные параметры навигации.
- На публичных страницах не должно быть переключателя версий карты.

### FR-02. Главная страница

- `Explore the cemetery` должен вести на `/cemetery` с v2.
- Сканирование GitHub на главной должно использовать слоты и могилы v2.
- Захоронение, начатое на главной, должно создавать запись v2 и завершаться на `/cemetery`.
- Callback после GitHub OAuth должен возвращать на канонический маршрут v2.

### FR-03. Новые захоронения

- Все браузерные и агентские захоронения должны отправлять `map_version = 'v2'`.
- Отсутствующий `map_version` на сервере должен интерпретироваться как `v2` после cutover.
- Явный `map_version = 'v1'` после cutover не должен создавать запись.
- Для явного v1-запроса API должен возвращать стабильную машинно-читаемую ошибку `CEMETERY_VERSION_RETIRED` и понятное сообщение о необходимости обновить клиент.
- Сервер остаётся единственным источником истины для лимита аккаунта, свободного слота и `grave_gid`.
- Повтор одного и того же локального `project_key` должен оставаться идемпотентным.

### FR-04. Перенос существующих могил

- Перенос всех существующих могил v1 является обязательным условием запуска, а не последующей cleanup-задачей.
- Каждая существующая могила v1 должна получить свободный v2 `slot_id` и совместимый с типом слота `grave_gid`.
- Значения `id`, `name`, `author_github`, `github_repo_id`, `project_key`, `created_at`, `f_count` и остальные мемориальные поля не меняются.
- Все `f_votes`, `grave_burn_intents` и `grave_burns` остаются привязаны к тому же UUID.
- Суммы и статусы GRAVE offerings не пересчитываются и не изменяются миграцией карты.
- `users.graves_count` и признак разблокированного пятого слота не меняются.
- После миграции публичных могил с `map_version = 'v1'` быть не должно.
- Нельзя отключать v1 route, закрывать public Storage или удалять v1 runtime до подтверждения, что каждая могила из pre-migration snapshot отображается в v2 и открывается по прежней ссылке `/grave/[uuid]`.

### FR-05. Ссылки и sharing

- `/grave/[uuid]` должен открывать `/cemetery?grave=[uuid]`.
- Существующие опубликованные UUID-ссылки должны продолжить работать без изменения URL.
- Meta-grave должен использовать `/cemetery?grave=meta`.
- Open Graph и share preview должны сохранять имя, эпитафию и остальные публичные поля могилы.
- Некорректный или отсутствующий UUID должен возвращать текущий корректный 404, а не открывать пустую карту.

### FR-06. Карта и церемония

- Перенесённые могилы отображаются при первой загрузке v2.
- Клик по перенесённой могиле открывает правильный memorial modal.
- Новое захоронение запускает церемонию на фактически записанном `slot_id`.
- После церемонии могила остаётся на карте и после перезагрузки.
- Одновременные захоронения не могут занять один слот.
- Спрайт каждой могилы должен соответствовать геометрии её v2-слота: tall, wide или large.

### FR-07. Локальный агент

- `src/agent/burial-helper.mjs` должен использовать v2 по умолчанию.
- Публичные agent instructions должны показывать `map_version: 'v2'`.
- Старый helper, отправляющий `v1`, получает `CEMETERY_VERSION_RETIRED` и не создаёт могилу в неверной карте.
- Receipt агента содержит рабочую ссылку `/grave/[uuid]`.

### FR-08. V1 runtime

- V1 Phaser scene не должна попадать в production bundle.
- `public/map/az.tmj` не должен раздаваться публичным приложением после cutover.
- В production-коде не должно остаться URL `/storage/v1/object/public/tilesets`.
- Переключатель карты, подписи v1 и инструкции по её запуску должны быть удалены или заменены описанием приватного архива.

### FR-09. Supabase Storage

- После production cutover публичный bucket/objects v1 должны стать недоступны без авторизации.
- После окончания окна восстановления v1-объекты удаляются из Supabase Storage.
- `NEXT_PUBLIC_SUPABASE_URL` остаётся в проекте, поскольку нужен API/авторизации; запрещается только использование URL Storage для картографических ассетов.
- Удаление должно затрагивать только предварительно проинвентаризированные v1-объекты или отдельный bucket, подтверждённый как принадлежащий исключительно v1.

## 8. Миграция данных v1 → v2

### 8.1. Обязательные входные данные

Перед созданием migration manifest необходимо получить:

- полный список могил v1 с `id`, `slot_id`, `grave_gid`, `created_at`;
- список уже занятых слотов v2;
- список auto-assignable слотов из актуального `cemetery-v2.tmj`;
- тип каждого целевого слота;
- допустимые `grave_gid` для tall, wide и large;
- количество связанных `f_votes`, `grave_burn_intents`, `grave_burns` и точную сумму verified offerings.

### 8.2. Migration manifest

До изменения базы создаётся явный, проверяемый manifest со следующими полями:

| Поле | Назначение |
|---|---|
| `grave_id` | Неизменяемый UUID могилы |
| `old_map_version` | Ожидается `v1` |
| `old_slot_id` | Значение для аудита и аварийного отката |
| `old_grave_gid` | Обычно `null`, сохраняется для аудита |
| `new_map_version` | Всегда `v2` |
| `new_slot_id` | Заранее выбранный свободный слот v2 |
| `new_grave_gid` | Совместимый визуальный вариант v2 |

Manifest не должен формироваться случайно во время production-транзакции. Он создаётся dry-run инструментом заранее и проходит визуальную и автоматическую проверку.

### 8.3. Политика размещения

- Рекомендуемый вариант: разместить существующие могилы как «первый ряд основателей» в заранее выбранной области v2.
- Могилы сортируются по `created_at`, затем по UUID для детерминированности.
- Целевые слоты перечисляются в manifest в желаемом визуальном порядке.
- Занятые v2-слоты исключаются.
- `grave_gid` выбирается детерминированно из пула, совместимого с типом слота.
- Специальные и meta-slots не используются.

### 8.4. Выполнение

Миграция выполняется одной транзакцией с коротким окном запрета новых захоронений:

1. Включить maintenance/write gate только для операций создания могил.
2. Сохранить приватный экспорт таблиц и контрольные суммы.
3. Повторно проверить preconditions manifest.
4. Заблокировать изменяемые строки могил на время транзакции.
5. Обновить только `map_version`, `slot_id` и `grave_gid` по UUID.
6. Выполнить все post-migration assertions.
7. При любой ошибке полностью откатить транзакцию.
8. После успешного production smoke снять write gate.

### 8.5. Обязательные инварианты

- Общее число могил до и после совпадает.
- Множество UUID до и после совпадает.
- Число v1-могил после равно нулю.
- Все `new_slot_id` уникальны внутри v2.
- Каждый `new_slot_id` существует в текущем TMJ.
- Каждый `new_grave_gid` допустим для типа целевого слота.
- Количество `f_votes`, `grave_burn_intents` и `grave_burns` совпадает.
- Сумма `amount_raw` для verified offerings совпадает точно, без округления.
- Ссылочная целостность не нарушена.
- `users.graves_count` не изменился.

## 10. Работа с лицензированными ассетами

### 10.1. До cutover

- Сделать приватную локальную резервную копию купленных файлов и подтверждения покупки.
- Хранить архив вне Git, публичных CDN и публичных Supabase buckets.
- Зафиксировать точный список Storage objects, используемых v1.
- Проверить, что bucket не используется другим проектом.

Ожидаемый набор v1 включает как минимум:

- `graveyard_ground.png`;
- `Graveyard_B.png`;
- `Graveyard_A2.png`;
- `Graveyard_C.png`;
- `non-rm-a1-square.png`;
- `Graveyard_D.png`;
- `Graveyard_A1.png`;
- `Crypt_D.png`;
- `Crypt_B.png`;
- `Fire_Animation.png`.

Фактический список определяется inventory bucket, а не только этим перечнем.

### 10.2. После cutover

1. Проверить, что production build не запрашивает эти объекты.
2. Сделать bucket приватным либо снять public read policy.
3. Проверить главную, карту и grave links с чистым browser cache.
4. Наблюдать приложение в течение окна восстановления.
5. Удалить только подтверждённые v1 objects или весь bucket, если доказано, что он выделен исключительно под v1.
6. Проверить падение Storage egress и отсутствие запросов к старым URL.

Публичный скриншот оригинальной v1 не создаётся. Допустимый публичный мемориал первой карте может быть сделан позднее только как новая композиция на собственных v2-ассетах.

## 11. План реализации

### Этап A. Подготовка репозитория

- Разобрать текущий большой dirty worktree и зафиксировать согласованный baseline отдельным коммитом.
- Не смешивать cutover с незавершёнными изменениями Web3/burn recovery и очисткой ассетов.
- Создать отдельный commit или ветку для v2 cutover.
- Повторно прогнать текущий baseline: unit, TypeScript, lint, build и browser suite.

Результат: воспроизводимая исходная точка без неидентифицированных изменений.

### Этап B. Кодовый cutover

- Перевести `/cemetery` на `CemeteryAppV2`.
- Настроить redirect со старых versioned routes.
- Перевести home scanner, OAuth callback и agent helper на v2.
- Запретить v1 writes.
- Удалить version switcher.
- Исправить canonical grave links.
- Добавить временный write gate для контролируемой production-миграции.

Результат: приложение умеет работать как v2-only, но ещё не удаляет v1 данные или Storage.

## 12. Тестовый план

### 12.1. Unit/API

- Omitted `map_version` создаёт v2.
- Explicit `v2` создаёт v2.
- Explicit `v1` возвращает retirement error и не вызывает insert RPC.
- Invalid version возвращает 400.
- Slot selection использует только auto-assignable v2 slots.
- `grave_gid` соответствует типу выбранного слота.
- Collision retry не меняет namespace.
- Account quota остаётся общей 4 + 1.
- Идемпотентный local retry возвращает исходную могилу.
- `/grave/[id]` формирует canonical v2 target.
- Старые cemetery routes сохраняют query при redirect.

### 12.2. Browser

- Desktop cold load `/cemetery`.
- Mobile cold load `/cemetery`.
- GitHub login callback возвращает в Bury modal.
- Создание могилы запускает церемонию.
- Перезагрузка сохраняет могилу.

- `/cemetery/v2?grave=X` перенаправляется и открывает X.

- Нет version switcher.
- Нет network requests к Supabase Storage `/tilesets`.

## 13. Критерии приёмки

Релиз считается принятым только при одновременном выполнении всех условий:

1. `/cemetery` показывает v2 на desktop и mobile.
2. Старые versioned routes ведут на `/cemetery` и сохраняют deep-link query.
3. Все существующие могилы видны в v2 и открываются по прежним UUID.
4. Число могил и множество UUID совпадают с pre-migration snapshot.
5. F и verified GRAVE offering totals не изменились.
6. В базе нет публичных могил v1.
7. Новые browser/agent burials создаются только с `map_version = v2`.
8. Новое захоронение проходит полный путь create → ceremony → reload → share link.
9. Production не запрашивает лицензированные v1 tilesets.
10. Public read старого Storage отключён.
11. Unit, TypeScript, lint, build и v2 browser tests проходят.
12. README и setup больше не предлагают запуск или загрузку v1 assets.
13. В Git отсутствуют лицензированные исходные PNG и публичный скриншот оригинальной v1.

Отключение v1 и закрытие Storage разрешается только после прохождения пунктов 3–5 для каждой существующей могилы, а не только по общему количеству записей.

## 14. Наблюдаемость после релиза

В течение первых 72 часов контролировать:

- `POST /api/graves`: долю 5xx и collision retries;
- `GET /api/graves`: ошибки и время ответа;
- количество новых строк v2 и отсутствие строк v1;
- client-side asset/load errors;
- открытие `/grave/[uuid]`;
- Supabase Database egress и Storage egress отдельно;
- прямые запросы к старым Storage URLs;
- корректность offering ledger и reverify jobs.

Любое расхождение UUID, числа могил или verified token totals является стоп-фактором и требует немедленного включения write gate.

## 15. Rollback

Публичный возврат к v1 не является штатным rollback из-за лицензионного риска. Штатный аварийный режим — maintenance page или откат на предыдущий проверенный v2-compatible deployment.

Для восстановления данных до переноса должны храниться:

- приватный pre-migration export;
- migration manifest с old/new значениями;
- контрольные суммы связанных таблиц;
- приватный архив v1-ассетов вне Git и публичного Storage.

Если post-migration assertions падают внутри транзакции, выполняется автоматический rollback. Если критическая проблема обнаружена после commit, новые writes блокируются, а обратное обновление `map_version`, `slot_id` и `grave_gid` выполняется строго по manifest. Даже в этом случае v1 не публикуется автоматически: до исправления v2 пользователю показывается maintenance state.

## 16. Риски и меры контроля

| Риск | Мера |
|---|---|
| Потеря или подмена UUID | UUID запрещено изменять; сравнение множеств до/после |
| Коллизия слотов v2 | Явный manifest, проверка занятых слотов и транзакция |
| Неверный размер спрайта | Проверка совместимости `grave_gid` с типом слота |
| Старый клиент создаёт v1 | Серверный запрет v1 writes и стабильный retirement error |
| Потеря F/burn history | Не менять grave ID; сверять counts и raw totals |
| Старый direct Storage URL продолжает тратить egress | Снять public policy, затем удалить objects |
| Невозможность отката | Export + manifest + write gate + maintenance mode |
| Смешивание с текущими незакоммиченными изменениями | Отдельный baseline и отдельный cutover commit |
| Лицензионное нарушение через архивный скриншот | Не публиковать оригинальную v1 или её скриншот |
| Реальная token-транзакция во время теста | Только mocked/read-only проверка без отдельного разрешения |

## 17. Definition of Done

Работа завершена, когда v2 является единственной публичной картой, все реальные могилы и их история доступны в ней, новые записи невозможно создать в v1, v1 runtime отсутствует в production, а Supabase Storage больше не раздаёт лицензированные tilesets.

Отдельный счётчик открытий v1, cron для её отключения и публичный визуальный архив после этого не требуются.
